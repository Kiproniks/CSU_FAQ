CSU FAQ — подробное техническое описание
========================================

1) Общая идея проекта
---------------------
Проект отвечает на вопросы по книгам "Гарри Поттер" через RAG-пайплайн.
RAG = Retrieval Augmented Generation:
1. Сначала ищем релевантные фрагменты в базе знаний.
2. Потом формируем ответ на основе найденного контекста.

В проекте есть два режима поиска:
- ChunkBased (по чанкам текста через embedding/Chroma);
- EntityBased (по сущностям + TF-IDF/overlap).

Интерфейсы:
- Web: app/web_app.py
- Telegram bot: app/telegram_bot.py
- Общая логика ответа: app/rag_pipeline.py


2) Поток обработки вопроса
--------------------------
Для Web и Telegram шаги одинаковые:
1. Пользователь задает вопрос.
2. Выбирается режим: chunk или entity.
3. RAGPipeline ищет релевантные фрагменты.
4. LLM (ollama, модель llama3.2:2b) генерирует финальный ответ.
5. В PostgreSQL логируется запрос, режим, ответ, модель, задержка.

Файл, где объединяется retrieval + LLM:
- app/rag_pipeline.py

Файл, где настроены провайдеры LLM:
- app/llm_service.py


3) ChunkBased — как работает
----------------------------
ChunkBased (ChunkBased/ChunkBased.py) делает так:
1. Текст книг режется на чанки (параметры chunk_size, overlap).
2. Для каждого чанка строится embedding.
3. Embedding сохраняются в Chroma (локально в chroma_db).
4. На вопрос пользователя ищутся top-k ближайших чанков.
5. Из top-k выбираются лучшие кандидаты (с учетом MMR/diversity).

Основные параметры:
- CHUNK_SIZE
- CHUNK_OVERLAP
- TOP_K_CHUNKS
- CHUNK_SPLITTER_MODE
- CHUNK_MMR_LAMBDA

Практический смысл:
- chunk_size маленький: выше точность фразы, но можно терять контекст;
- chunk_size большой: больше контекста, но больше "шума";
- top_k выше: больше кандидатов, но медленнее и риск лишнего контекста.


4) EntityBased — как работает
-----------------------------
EntityBased (EntityBased/EntityBased.py) работает по сущностям:
1. Для чанков извлекаются сущности (персонажи, места, ключевые слова).
2. Вопрос раскладывается на токены/сущности.
3. Считается релевантность по сочетанию:
   - TF-IDF совпадения;
   - overlap сущностей;
   - MMR штраф/разнообразие.
4. Возвращаются top-k фрагментов.

Основные параметры:
- TOP_K_ENTITIES
- ENTITY_CHUNK_SIZE
- ENTITY_CHUNK_OVERLAP
- ENTITY_MIN_LENGTH
- ENTITY_MAX_ENTITIES_PER_CHUNK
- ENTITY_TFIDF_WEIGHT
- ENTITY_OVERLAP_WEIGHT
- ENTITY_MIN_SCORE
- ENTITY_MMR_LAMBDA

Практический смысл:
- EntityBased часто лучше на вопросах "кто/что/где", где важны имена;
- ChunkBased часто лучше на длинных "почему/зачем" за счет контекста.


5) Почему нужен PostgreSQL
--------------------------
PostgreSQL используется для:
- users (пользователи, роли, верификация);
- user_tokens (токены доступа);
- query_logs (история запросов и ответов);
- benchmark_* таблицы (результаты тестов);
- chunk_store/entity_store (сохранение чанков/сущностей в БД).

Ключевой момент:
- Если PostgreSQL недоступен, FAQ/аналитика/часть админ-функций работают ограниченно.

Подключение настраивается в .env:
- DATABASE_URL=postgresql://.../csu_faq


6) FAQ — как устроено сейчас
----------------------------
Сейчас реализован гибридный FAQ (app/faq_catalog.py):
1. Всегда показываются 10 фиксированных FAQ (база знаний).
2. Плюс до 10 динамических вопросов из query_logs (последние 100 запросов).
3. Дубли динамики с фиксированной базой отсекаются по нормализованному вопросу.

Где используется:
- Web /faq: app/web_app.py
- Telegram /faq и кнопка FAQ: app/telegram_bot.py

Это решает сразу две задачи:
- есть стабильный "каркас" FAQ;
- есть живой блок "что реально спрашивают пользователи".


7) Дообучение (LoRA) — что сделано
----------------------------------
Дообучение запускалось в Google Colab через LoRA (SFT):
1. Из QA-датасетов готовились train_sft.jsonl / val_sft.jsonl.
2. База: Qwen/Qwen2.5-3B-Instruct (в Colab).
3. Результат — адаптер LoRA (adapter_model.safetensors + adapter_config.json).

Важно:
- LoRA-адаптер не заменяет retrieval;
- он улучшает стиль/точность генерации, если подключен в runtime;
- финальное качество все равно сильно зависит от качества retrieval и датасета.

Текущий загруженный адаптер в проекте:
- run_20260323_075717/


8) Как делались тесты качества
------------------------------
В проекте было два типа тестов:

A) Бенчмарк настроек retrieval:
- Прогоны разных chunk/entity конфигов;
- Оценка semantic-judge (score 0..10);
- Сводка в Excel.

B) Контрольные "до/после" тесты:
- Папка: ВАЖНЫЕ ТЕСТЫ
- Один и тот же набор из 30 вопросов;
- Два отчета: до и после;
- Сравнение avg_score_10 и дельты.

Текущая логика прогона важных тестов:
- scripts/important_tests_eval.py
- Вопросы: ВАЖНЫЕ ТЕСТЫ/questions_30_hp.json
- Выгрузка: ВАЖНЫЕ ТЕСТЫ/до и ВАЖНЫЕ ТЕСТЫ/после


9) Что влияет на качество ответа сильнее всего
-----------------------------------------------
1. Качество датасета (корректные эталонные ответы, без противоречий).
2. Правильная индексация книг (чистый текст из PDF, корректный split).
3. Параметры chunk/entity (особенно top_k, chunk_size, overlap, mmr).
4. Доступность LLM (ollama должен быть поднят, иначе fallback).
5. Стабильная PostgreSQL (для FAQ и аналитики).


10) Технические замечания по эксплуатации
-----------------------------------------
1. Если видишь "PostgreSQL недоступен":
   - проверь, слушает ли порт 5432;
   - проверь корректность DATABASE_URL;
   - перезапусти web/bot после старта PostgreSQL.

2. Если Telegram молчит:
   - проверь, что запущен run_bot.py;
   - убери дубли процессов (двойной polling может мешать).

3. Если web отвечает долго:
   - первый запрос может быть медленнее (прогрев индекса и моделей).

4. Если LLM недоступна:
   - проверь Ollama и модель llama3.2:2b;
   - проверь OLLAMA_BASE_URL.


11) Краткий итог архитектуры
----------------------------
Проект уже построен как рабочая RAG-система:
- retrieval слой (chunk/entity),
- generation слой (LLM),
- storage слой (PostgreSQL + Chroma),
- интерфейсы (Web + Telegram),
- контроль качества (бенчмарки и важные тесты до/после).

Ключевой текущий вектор улучшения:
- подключить лучший LoRA-адаптер в runtime;
- фиксировать регрессии по контрольному набору вопросов (ВАЖНЫЕ ТЕСТЫ).
